## Part A: memory (FUTURE.md §4)

New tests (registry rows added next to their groups; ids work with `--run`):

| Id | Group / name | Default | Result | What |
|---|---|---|---|---|
| `mem.grid` | Cache & memory / L1 / L2 / L3 / DRAM grid | on | values (16) | AIDA64-style grid: read / write / copy GB/s with all threads, latency ns with one thread, per level |
| `mem.bw.mix` | DRAM bandwidth / Read / write mix | on | values (4) | Read only, 3:1, 2:1, 1:1 read:write, all threads, DRAM |
| `mem.bw.scaling` | DRAM bandwidth / Thread scaling | on | series, x = threads | DRAM read and non-temporal write at 1, 2, ... one thread per core, then all LPs |
| `mem.lat.loaded` | Latency / Loaded latency (vs bandwidth) | on | series, x = delay cycles | Intel MLC style: latency on the best core while the other cores generate throttled read traffic |
| `mem.lat.pages` | Latency / 4 KiB vs 2 MiB pages | off | series, x = bytes | Pointer-chase latency 1 MiB–256 MiB in both page sizes; skipped without SeLockMemoryPrivilege |

Metric names (TOON `metrics[]`):
- `mem.grid`: `L1 read`, `L1 write`, `L1 copy` (GB/s), `L1 latency` (ns), same for `L2`, `L3` (omitted when the CPU has
  no L3) and `Memory`.
- `mem.bw.mix`: `Read only`, `3:1 read:write`, `2:1 read:write`, `1:1 read:write` (GB/s, bytes read + written).
- `mem.bw.scaling`: `Read`, `Write (non-temporal)` per x = thread count.
- `mem.lat.loaded`: `Latency` (ns) and `Bandwidth` (GB/s, generated by the load threads) per x = delay cycles per 256 B
  (100000, 20000, 10000, 5000, 2500, 1200, 600, 300, 150, 75, 0). x is the delay, not the measured bandwidth, so runs
  align in the compare window.
- `mem.lat.pages`: `4 KiB pages`, `2 MiB pages` (ns) per x = working set.

Design:
- Grid working sets. Bandwidth, every thread on its own block: L1 = L1D / 2 / threads-per-core, L2 = L2 / 2 / threads-
  per-core, L3 = 3/4 of all L3 / threads, DRAM = min(arena, 1 GiB) / threads. Copy moves the first half of the block to
  the second and counts read + written bytes (as `mem.bw.copy`). Latency (best core, 4 KiB pages): L1D / 2, L2 / 2,
  max(2 x L2, one L3 instance / 2) capped at 3/4 of the L3 instance, 256 MiB. Stores are normal (RFO) stores; NT
  write numbers stay in `mem.bw.write`. Phases are duration / 4 (min 0.25 s), 16 phases: ~12 s at the default 3 s.
- With 8 cores / 16 threads and 16 MiB L3 the L3 block is 768 KiB per thread = 1.5 MiB per core, 1.5x the 1 MiB L2,
  so the L3 row is mostly (not only) L3 traffic. There is no clean all-threads L3 test on CPUs whose L3 per core is
  ~2x the L2; AIDA has the same issue.
- Loaded latency: worker 0 (best core) chases a 256 MiB random cycle; one load thread on every other physical core
  (SMT siblings idle, so only the memory system is shared) reads its own region (up to 256 MiB) with `k_mem_read_delay`:
  256 B of loads, then a `dec`/`jnz` loop of N iterations. Bandwidth = sum of the load threads' bytes / time.
- Read/write mix kernel `k_mem_mix`: per 128 B stored, 1 / 2 / 3 x 128 B loaded; the stored data is the XOR of the
  loads so nothing can be dropped.
- Large pages: `big_alloc_large` needs SeLockMemoryPrivilege ("Lock pages in memory", secpol.msc > Local Policies >
  User Rights Assignment), which no account has by default, admins included. Without it `mem.lat.pages` is SKIPPED with
  that reason (that's why it's off by default); `mem.lat.chase` keeps its existing behaviour (2 MiB pages when possible).
- Arena rule kept: all new tests use the suite arena (min(1.5 GiB, ¼ of free RAM)); extra allocations are the
  pointer-chase permutation (16 MiB for 256 MiB) and, for `mem.lat.pages`, a large-page buffer of at most
  min(arena / 2, 1 GiB) only when ¼ of free RAM covers it.
- Shared helpers moved out of `mem_latency`: `chase_build`, `chase_ns`, `mem_point_seconds` (`mem/mem_internal.h`).

GUI: the Charts tab got a grid table for `mem.grid` (rows L1 / L2 / L3 / Memory, columns Read / Write / Copy /
Latency) and a latency-vs-bandwidth XY plot for `mem.lat.loaded` (`app/mem_charts.*`). Generic series charts now draw
one plot per metric name (needed for the two-metric series; previously all points went into one line).

Working set: `mem_init` now raises the process working-set minimum (soft, `SetProcessWorkingSetSizeEx`) by the arena
+ 64 MiB and restores it in `mem_shutdown`. Before that, with ~8 GB free and ~11 agents building / testing, a 1 GiB
chase read 1.4 µs and the loaded-latency idle point 900 ns (pages trimmed and soft-faulted back). With it: 134 ns
(grid DRAM latency) vs 144 ns (`mem.lat.chase` 256 MiB) in the same run.

builds and tests; L3-range latency is inflated by it — `mem.lat.chase` itself read 95–99 ns at 4–8 MiB in the same run,

## Part B: system information (FUTURE.md §9)

Three cost tiers (`core/sysinfo_ext.h`):
1. `g_cpux` (`sysinfo_cpu.cpp`), filled in `sysinfo_init`: codename + microarchitecture (family/model table, AMD Zen 1–5,
   Intel Skylake–Panther Lake), microcode (registry `Update Revision`: Intel = high dword, AMD = one dword), base clock
   (registry `~MHz`), max clock / bus clock / socket (SMBIOS type 4; "max speed" is vendor-filled, 5100 MHz here = the
   boost clock), ~95 CPUID feature flags (Linux-style names), caches with ways / line / instances
   (GetLogicalProcessorInformationEx), core map (CPU sets: LPs per core, EfficiencyClass, SchedulingClass = preferred
   core rank, last-level-cache group), P / E split on hybrid CPUs.
2. `g_dev` (`sysinfo_devices.cpp`, `sysinfo_display.cpp`), lazy via `devices_ensure()` (System details window, report,
   results files): one cfgmgr32 walk of the PnP tree → PCI tree (location, IDs, class from the compatible IDs, PCIe link
   current / max), USB tree (controllers, hubs, devices; composite interfaces skipped), chipset, network adapters
   (GetAdaptersAddresses: name, type, status, link speed; no MAC / IP on purpose), audio endpoints (MMDevice: name,
   direction, mix format, default), displays (QueryDisplayConfig + EDID), driverless GPU details (devnode driver date /
   provider / PCIe link, D3DKMT WDDM version, chip and video-BIOS strings, max memory clock, max memory bandwidth when the
   driver reports it), DXGI tearing support and the Windows VRR-optimizations setting.
3. `g_gpux` (`sysinfo_gpu.cpp`), only on request because it creates a Vulkan instance and a D3D12 device: Vulkan API
   version, driver name / info, extension list, compute units (AMD `VK_AMD_shader_core_properties2` active CUs, NVIDIA
   `VK_NV_shader_sm_builtins` SMs), subgroup size, Resizable BAR (size of the DEVICE_LOCAL | HOST_VISIBLE heap: > 512 MiB
   = on; integrated GPUs n/a), D3D12 max feature level, highest shader model, raytracing / mesh / VRS / sampler-feedback
   / binding tiers, GPU upload heaps (OPTIONS16, needs ReBAR).

**GPU-details hook for the GPU suites:** `gpu_api_details_query(u32 gpu)` (sysinfo_ext.h) fills `g_gpux[gpu]` and sets
bit `gpu` of `g_gpux_ready` (release) when complete. Blocking, ~1–2 s per adapter (Vulkan instance + D3D12 device). Call
it from `gpu_vk_init` / `gpu_d3d12_init` for `p->gpu_adapter` (the GPU is awake there anyway), e.g. only when its bit
isn't set yet; results files written afterwards then carry the details under `system.details.gpuN`. I didn't edit
`src/gpu/`. Never call it at startup.

Chipset (`chipset_query`): AMD root-complex and desktop-chipset device IDs from pci.ids (pciutils, 2026-11-09):
`AMD <series> chipset` when a 300/400/500/600/800-series chipset function is present, else `AMD <platform> SoC (no
separate chipset)` from the root complex (bus 0 dev 0 fn 0) — e.g. "AMD Phoenix / Hawk Point SoC" here. Intel: the
LPC / eSPI bridge's Windows name (Intel's chipset INF names the model, e.g. "Z790 LPC Controller"); without the INF it
says "Intel PCH (8086:xxxx)". Intel 100-series+ LPC IDs weren't collected (pci.ids too long to fetch verbatim).

Displays: active paths (mode, refresh, connector from outputTechnology, driving GPU by LUID, advanced color
supported / on) + EDID from the monitor devnode's registry (name from the 0xFC descriptor or the last 0xFE string for
laptop panels, PNP maker + product, preferred timing = native mode, diagonal, VRR range from the range-limits
descriptor when the continuous-frequency bit is set or from the AMD FreeSync / HDMI Forum VSDB, HDR from the CTA HDR
static-metadata block). Here: "MNF601BA1-4", CSW, internal, 1920x1080, VRR 48–144 Hz, HDR block present, 15.3 in.

Not available without a vendor API / driver (left out): GPU memory type (GDDR6/7) and bus width (the driver's max
memory bandwidth would give it but neither GPU here reports it), NVIDIA shader count (SMs are reported; FP32 lanes per
SM differ by generation), USB link speed (needs hub IOCTLs), per-display VRR on/off state.

System report (`core/sysreport.cpp`): one model — sections of key/value lines, tables, notes (`SysReport`) — rendered
three ways: the **System details** tool window (`app/system_ui.*`, `--tool system`, "Details" chip button on the System
row: section list + content; Refresh, "Query GPU APIs" on a worker thread (disabled during runs), Copy report (plain
text to the clipboard; Save report was removed 2026-11-12, the CLI `--sysinfo <base>` still writes files)), plain text
(`sysreport_text`) and TOON (`sysreport_toon`). CLI: `--sysinfo [base]` prints the full report (queries the GPU APIs
first) and with a path writes `<base>.txt` / `<base>.toon.txt`. The CLI header also prints a codename / microcode line;
the GUI's System CPU line shows codename + microarchitecture.

TOON in results files: `results.cpp` `write_system` ends with `sysreport_write_results(f, 1)`, which writes
`system.details` with the sections marked "in results": `cpu` (name, codename, microarchitecture,
family_model_stepping, microcode, socket, cores_threads, [performance_efficient_cores, l3_groups_ccx_ccd], base_clock,
max_clock_smbios, bus_clock, instruction_sets, `caches[N]{level,type,size,ways,line,instances}`), `board` (system,
board, bios, chipset, host_bridge), `gpu0`.. (name, pci_id, memory, driver with date + provider, wddm, scheduling, chip,
video_bios, pcie_link, max memory clock / bandwidth; plus the D3D12 / Vulkan keys once `g_gpux` is filled), `displays`
(tearing, VRR setting, `displays[N]{name,maker,connector,adapter,mode,native,vrr_range,hdr,size}`). Values are display
strings ("3294 MHz"). `compare.cpp` ignores the block (verified: unknown keys / tables are skipped). Memory section:
a note that SPD contents and memory timings need a kernel driver (not read; `memory_section` in sysreport.cpp).
